# バージョンアップの提案 2026-11

**これは提案だけで、実装していません。** 2026-11 の点検で分かった現状の課題(`docs/audit-2026-11.md`)と、
利用者(日本語話者の個人・家族。バンコク在住の家族が使う想定)の使い方を踏まえて、現実的なものを選びました。

規模の目安: **小**=半日、**中**=1〜2日、**大**=それ以上。
費用の話は、Google の料金・無料枠が変わることがあるため、**金額は書かず、増えるかどうかと確認先だけ**を書いています(Google Maps Platform の最新の料金表で確認してください)。

## 1. Google マップへの連携(開く・共有リンク)

1. **何をするか**:各スポットに「Google マップで経路を開く」、お気に入りや検索結果の複数スポットを順に回る「Google マップのルート共有リンク」、「LINE などで送る」(Web Share API)を追加する。
2. **利用者のメリット**:現地ではいつもの Google マップアプリのナビを使える。家族に「ここに行こう」をすぐ送れる。アプリ内の経路は Routes API の課金対象だが、マップアプリを開くだけなら課金なし。
3. **実現方法**:Google マップの URL スキーム(`https://www.google.com/maps/dir/?api=1&origin=…&destination=…&waypoints=…&travelmode=…`、`maps/search/?api=1&query=…&query_place_id=…`)で URL を組み立てるだけ。既存の `placeId`・座標・`safeHttpUrl`・`createExternalLink` をそのまま使える。追加するのは URL を組み立てる純粋関数(テストしやすい)とボタン数個。経由地の数に上限があるため、上限で切って案内を出す。
4. **規模**:小
5. **リスクと費用**:API 課金なし。URL の組み立て規則の変更(仕様が変わる可能性)、経由地の上限。位置情報を URL に含めて共有する場合、共有先に現在地が伝わる点を画面で明示する。
6. **おすすめ順位**:**1**(最小の工数で最も実用的。リスクが最も低い)

## 2. タイ・日本の地域プリセット(ジャンル・言語・起点の保存)

1. **何をするか**:検索の起点を「現在地」だけでなく**よく使う場所**(ホテル・自宅・職場など)として名前をつけて保存し、ワンタップで選べるようにする(「地図上の指定」もあわせて検討)。タイ向けのジャンル(寺院・市場/ナイトマーケット・ショッピングモール・マッサージ/スパ・屋台街・動物園/水族館など)と、日本向け(現在のジャンル)を**地域で切り替え**。表示言語(日本語/英語/タイ語)を、Places の `languageCode` と Wikipedia の言語に反映。
2. **利用者のメリット**:バンコク滞在中も日本でも、同じアプリで「その土地らしい」検索ができる。現在は検索の説明文・Wikipedia が日本語固定のため、タイの施設は日本語の情報が少ない(英語・タイ語の併記で補える)。
3. **実現方法**:`js/config.js` の `GENRES` に地域別のセットを追加(Places API (New) の「タイプ」の一覧で、タイの施設に使える型を確認して選ぶ)。`places.js` の `REQUEST_LANGUAGE_CODE` を設定値にする。起点の保存は、既存の `favorites` と同様の小さな新テーブル(DB の新しいマイグレーションが必要。RLS は同じ「自分の行だけ」)か、端末の localStorage のみ(ログイン不要・最小)。`description.js` の「日本語率」の判定(`isMostlyJapanese`)は言語設定に合わせて切り替える。
4. **規模**:中
5. **リスクと費用**:API 呼び出し回数は増えない(言語・タイプの指定のみ)。タイ語・英語の説明文を自動生成するとテンプレートの翻訳作業が必要。タイのタイプの精度は実地で確認が必要(**バンコクの実在の場所で試すため、テスト用の座標は公開の地点(寺院・駅)を使い、個人の住所を入れない**)。
6. **おすすめ順位**:**2**(バンコクの家族の使い方に直結。費用リスクが低い)

## 3. お気に入りへのメモ・訪問済みの記録

1. **何をするか**:お気に入りに「メモ」(例: 「子供が喜んだ」「午前に行く」)と「訪問済み(日付)」「行きたい」の区別を付ける。一覧で絞り込み(行きたい/訪問済み)。
2. **利用者のメリット**:旅の計画と思い出の記録を、同じ場所の一覧で管理できる。複数端末で共有される。
3. **実現方法**:`tourist_app.favorites` に列を追加(`note text`・`visited_at date`・`status text`)し、**`update` のポリシーと権限を新たに追加**(現在は意図的に update が無い。自分の行だけ・`with check` 付き・列の長さの制約付き)。`favorites.js` に更新関数、`ui.js` に編集 UI(`textContent` で描画するという現在の方針を維持)。新しいマイグレーションを足す形(`schema.sql` は書き換えない)。
4. **規模**:小〜中
5. **リスクと費用**:API 課金なし。メモはユーザーが自由に入力する文字列なので、必ず `textContent` で表示し、長さの上限を DB と画面の両方で付ける。**update 権限の追加は DB の変更で、本番での実行はあなたが行う**。個人の行動の記録(訪問済みの日付)が Supabase に増えるため、README のプライバシーの表を更新する。
6. **おすすめ順位**:**3**(工数が小さく、日々の使い勝手が上がる。update ポリシーを RLS の観点で正しく足す良い機会)

## 4. 子連れ向けフィルター(トイレ・ベビーカー・屋内/日陰)

1. **何をするか**:検索結果に「子供連れ向きか」「トイレあり」「ベビーカー/車いすで入れるか」「屋内(暑さ・雨の日向け)」などの絞り込みと表示を追加する。バンコクの暑さ・スコールを想定した「屋内中心」のジャンル(ショッピングモールの遊び場、水族館、屋内の遊び場、カフェ)。
2. **利用者のメリット**:子連れでの「行ってみたら使えなかった」を減らせる。
3. **実現方法**:Places API (New) には、`goodForChildren`・`restroom`・`accessibilityOptions` などの属性フィールドがある(どのフィールドが使えるか・どの料金区分かは、最新の Places API (New) のドキュメントで確認)。`PLACE_FIELD_MASK` に追加し、`places.js` の絞り込みに条件を足す。属性が未登録の場所は「不明」として扱う(除外しない)。「日陰」は属性がないため、タイプ(公園・屋内施設)と説明文からの推定にとどまる。
4. **規模**:中
5. **リスクと費用**:**追加するフィールドによって、1 回の検索の料金区分が上がる可能性がある**(現在も `reviews`・`editorialSummary` などを含めており、すでに高い側の可能性がある=点検の F-20)。実装前に料金を確認し、「属性を取得する検索」を、ユーザーが明示的にオンにしたときだけにする設計を推奨。属性のデータは欠けていることが多い。
6. **おすすめ順位**:**4**(価値は高いが、費用の確認が先。F-20 の見直しとセットで)

## 5. API キーをブラウザに置かない(サーバー側の中継)

1. **何をするか**:Places / Routes の呼び出しを、ログイン済みの家族だけが使える**サーバー側の中継**(Supabase Edge Functions など)経由にして、Google の API キーをブラウザ・localStorage に置かないようにする。
2. **利用者のメリット**:キーの入力が不要になる(家族に「キーを入れてください」と頼まなくてよい)。XSS や端末の共有でキーが盗まれる心配がなくなる。登録した家族以外は API を使えず、不正利用による請求も防げる。
3. **実現方法**:Edge Function が、Supabase のログイン(JWT)を検証し、サーバー側に保管したキーで Places / Routes を呼ぶ。`js/http.js` の `postGoogleApi` を差し替えるだけで呼び出し側は変えずに済む(点検で通信を共通化してある)。地図の表示(Maps JavaScript API)にはブラウザ側のキーが引き続き必要だが、**HTTP リファラー制限と Maps JavaScript API のみの制限**を付けた別のキーにでき、被害が小さい。リクエストの上限(1 人あたり・1 日あたり)もサーバー側で数えられる。
4. **規模**:中〜大
5. **リスクと費用**:Edge Functions の利用量(家族用なら無料枠の範囲に収まる見込みだが、確認が必要)。**本番のサーバー側の設定(キーの保管・デプロイ)はあなたの作業**。中継自体の認可の不備(誰でも呼べる)が新しいリスクになるので、JWT の検証・入力の検査・上限をテストで固める。共有プロジェクトに関数を置く場合は、他アプリへの影響に注意(専用プロジェクトへの分離とセットが望ましい)。
6. **おすすめ順位**:**5**(安全面の効果は最大。ただし工数が大きいので、1〜4 の後。キーの制限が正しく設定されていれば急ぎではない)

## 6. 「今開いている」「天気」を考慮したおすすめ

1. **何をするか**:「今開いている場所だけ」の絞り込み、営業時間の表示(今日の営業時間)、雨・猛暑のときに屋内のジャンルを上位にする、天気の簡単な表示。
2. **利用者のメリット**:行ってみたら閉まっていた、雨で外の観光地だった、を減らせる。現在の説明文は営業時間を文章化して並べているため、「今開いているか」が一目で分からない。
3. **実現方法**:営業状況は Places の `currentOpeningHours`(営業中か)/ 既に取得している `regularOpeningHours` から計算。天気は、キー不要・ブラウザから呼べる公開の天気 API(Open-Meteo など。利用規約・商用利用の可否を確認すること)を使い、CSP の `connect-src` にそのホストを追加する。「雨なら屋内」は `GENRES` のジャンルに `indoor: true` を持たせて並び替えに反映。
4. **規模**:中
5. **リスクと費用**:`currentOpeningHours` は料金区分が高い側のフィールドの可能性(案 4 と同様に確認)。タイは時差・祝日(仏教の祝日など)で、営業時間のデータが実際と異なることがある。天気 API の可用性・利用規約。
6. **おすすめ順位**:**6**

## 7. 旅程づくり(日ごとに並べ、移動時間つき・順序の最適化)

1. **何をするか**:複数の候補を「1日目・2日目」に並べ、スポット間の移動時間・距離を表示し、回る順序を最適化する。ホテルを出発・帰着にして、1日の所要時間の目安を出す。
2. **利用者のメリット**:旅行の計画を、このアプリの中で完結できる。
3. **実現方法**:Routes API の `computeRoutes`(経由地+`optimizeWaypointOrder`)または `computeRouteMatrix`。新しいテーブル(`trips`・`trip_items`。RLS は「自分の行だけ」。共有する場合は案 8 と設計をそろえる)。既存の `fetchRoute`/`parseRouteResponse`・`formatDuration`・地図の `renderRoute` を再利用。
4. **規模**:大
5. **リスクと費用**:**Routes API の経由地の最適化・ルート行列は、通常の経路より料金区分が高い**。バンコクの交通渋滞・公共交通機関の情報の精度。DB の新テーブル(マイグレーション。本番での実行はあなた)。実装前に、1 回の旅程づくりの API 呼び出し回数を見積もり、クォータ・予算アラートの範囲内か確認する。
6. **おすすめ順位**:**7**(価値は高いが工数・費用が大きい。1〜3 で土台を作った後)

## 8. 家族との「行きたい場所」リストの共有

1. **何をするか**:お気に入りを、家族・同行者と共有する「リスト」にする(リストごとにメンバーを招待。全員が追加・閲覧できる)。
2. **利用者のメリット**:日本とバンコクに分かれている家族でも、同じリストを見ながら計画できる。
3. **実現方法**:`lists`・`list_members`・`list_items` のテーブルを新設し、**RLS で「メンバーだけが見える・自分が属するリストにだけ追加できる」**を表現する(自己参照の RLS は無限再帰になりやすいので、`security definer` の補助関数を使うか、メンバーシップの設計を工夫する必要がある。作る場合は、本番での実行前にローカルの PostgreSQL で検証するスクリプト `supabase/tests/local-rls-test.sh` の形式を拡張して、他人のリストが見えないことをテストで固めること)。招待は共有リンク(推測できないトークン)かメールで。
4. **規模**:大
5. **リスクと費用**:API 課金なし。**RLS の誤りが、他人のデータの漏えいに直結する**(最もセキュリティ上の注意が必要な案)。招待リンクの漏えい・失効、メンバーの退出・削除。共有プロジェクトでの影響(点検の F-01)があるため、**専用の Supabase プロジェクトに分けてから**行うことを強く推奨。
6. **おすすめ順位**:**8**(価値は高いが、リスクと工数が最大)

## 検討したが見送った案

- **PWA(オフラインで保存済みの場所を見る)**:Google Maps Platform の利用規約では、Places のデータのキャッシュに制限がある(場所の ID は保存できるが、それ以外は原則として長期保存できない)。オフラインで見られるのは「自分のメモ・お気に入りの名前・座標」程度に限られ、ネットが無いと地図も出ない。案 3(メモ)の後で、「何をオフラインにするか」を決めてから検討する。
- **Google のキーなしで使える代替(OpenStreetMap の Overpass / Nominatim)**:公開サーバーは利用規約で大量・商用的な利用が制限され(User-Agent・間隔・キャッシュのルール)、評価・レビュー・営業時間・写真が無い。このアプリの価値(おすすめ順・説明文)を満たせないため、見送り。やるなら「キーを入力しなくても使える簡易モード」の位置づけで、規約の確認が先。
- **anon キーの更新**:`js/config.js` の Supabase の anon キー(JWT)は、有効期限が 2036 年。その年までに、Supabase 側でキーを更新し、設定を更新する必要がある(保守のメモ)。

## 次の 1 セッションでやるなら、この 3 つ

**案 1(Google マップへの連携)+ 案 2 の「起点の保存」部分 + 案 3(お気に入りのメモ・訪問済み)** を推奨します。

| 理由 | 内容 |
|---|---|
| 費用・リスクが低い | 3 つとも、Google の API の呼び出しが増えず、追加の課金がほとんどない。点検で見つかった「キーの制限」や「共有プロジェクトの確認」の完了を待たずに進められる |
| 家族の使い方に直結 | 現地で「マップアプリで開く」(案 1)、「ホテルを起点に検索」(案 2 の一部)、「行った・行きたい」の記録(案 3)は、毎回の旅行で使う |

| 土台が整う | 案 3 で `update` ポリシーを RLS 付きで正しく足す経験が、のちの案 7・8(DB を使う大きな機能)の準備になる |

案 2 のタイ向けジャンルと言語の切り替え(後半)は、実際のバンコクの場所での確認が必要なので、その次のセッションに回します。
