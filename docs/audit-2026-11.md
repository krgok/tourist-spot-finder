# 点検レポート 2026-11

対象: 観光地調査アプリ(静的 Web アプリ + Supabase)。実施日: 2026-11-05。
このレポートに、秘密の値・個人情報は書いていません(見つかったものは場所と種類だけ記載)。

## 1. 結論(先に読む部分)

- **秘密の混入は、履歴を含めて見つかりませんでした。** Google の API キー・`service_role`・パスワード・トークンはありません。JWT は 1 種類だけで、`role=anon`(公開前提の値)です。
- **Supabase の RLS は、書き方としては正しい**(両テーブルで有効・「自分の行だけ」・`using (true)` なし・`security definer` やビューなし・他人の ID での insert 不可)。ただし**権限が広すぎる(`grant all`)・入力と件数の上限がない**ため、補強のマイグレーションを用意しました(**本番への実行はあなたが行います**)。
- **最大の未解決リスクは、アプリの外にあります**:このアプリは公開 URL で Google ログインを提供しているため、**誰でも、この共有 Supabase プロジェクトにユーザー登録できます**(= `authenticated` ロールを得られます)。他アプリのテーブルが「ログイン済みなら誰でも読める」設定だと、見知らぬ人に見えてしまいます。私はそれを確認できないので、`supabase/audit-queries.sql` をあなたが実行して確認してください(§4)。確認するまでは、この項目を最優先にしてください。
- アプリ側では、**実在の XSS(施設名を HTML として情報ウィンドウに渡していた)**と、**Wikipedia の一時的な失敗で検索全体が失敗する**など、実害のある不具合を直しました。
- **Google の API キーは、設計上ブラウザに平文で置かれます。** キーに「HTTP リファラー制限」「API の制限」「クォータ」「予算アラート」をかけているかが、被害を左右します。**この確認は、あなたの作業です**(§6 の 1)。

## 4. Supabase の権限表(RLS)

`supabase/schema.sql` を 1 行ずつ読んで作成し、ローカルの使い捨て PostgreSQL(Supabase のロール・`auth.uid()` は最小のスタブ)で、**変更前後の両方**の挙動を確認しました。

| | favorites / search_history |
|---|---|
| **変更前(schema.sql のみ)** | |
| 未ログイン(anon) | select は 0 行(RLS)、insert は拒否、delete は 0 行。ただし**テーブル権限は `grant all`**(TRUNCATE・REFERENCES・TRIGGER を含む。TRUNCATE は RLS の対象外。PostgREST 経由では現状呼べない) |
| ログイン済みの本人 | select / insert / delete は自分の行だけ。update は**ポリシーなし = 不可**(アプリに update 処理はなく、意図どおり) |
| ログイン済みの他人 | 本人の行は見えない・消せない(0 行)。他人の `user_id` での insert は `with check` で拒否 |
| **変更後(マイグレーション適用後)** | |
| 未ログイン(anon) | すべて**権限エラー**(スキーマの usage も無し) |
| ログイン済みの本人 | select / insert / delete のみ(自分の行だけ)。update・truncate は権限なし |
| ログイン済みの他人 | 同上(見えない・消せない・他人 ID での insert は拒否) |

確認した「ポリシーを通らない経路」: `using (true)` のポリシーなし/RLS 無効のテーブルなし/`security definer` の関数なし/ビューなし(いずれも `tourist_app` 内)。
**`tourist_app` の外(他アプリのスキーマ)は、ここからは見えません。** 次の手順で確認してください(`supabase/audit-queries.sql` は読み取り専用です):

1. SQL Editor で `supabase/audit-queries.sql` を実行する。
2. 次の行が**出たら要対応**: ①(RLS 無効で anon/authenticated に権限があるテーブル)②(`using (true)` のポリシー)③(anon / PUBLIC への広い権限)⑤(`security definer` で anon が実行できる関数)⑥(`security_invoker` でないビューで anon が select できるもの)。
3. 特に ②③ で `authenticated` が絞られていないテーブルがあれば、**誰でもサインアップできる現状では、見知らぬ人に読まれる**ことになります。各アプリ側で修正してください。
4. このアプリが共有プロジェクトのリスクの源にならないよう、**家族全員が一度ログインしたら、Authentication の「Allow new users to sign up」をオフ**にしてください。最も確実なのは、このアプリ専用の Supabase プロジェクトに分けることです。

### F-14 の既存データの掃除(任意)

古い版で保存されたお気に入りの `snapshot` には、レビュー等が残っています。Supabase の SQL Editor で、まず件数を確認してから実行してください(あなた自身のデータを変更する操作なので、私は実行していません。ローカルの使い捨て DB で動作確認済み)。

```sql
-- 件数の確認
select count(*) from tourist_app.favorites where snapshot ?| array['reviews','photos','_wikipedia'];
-- 掃除(レビュー・写真・Wikipedia 本文を取り除く)
update tourist_app.favorites
set snapshot = snapshot - 'reviews' - 'photos' - '_wikipedia'
where snapshot ?| array['reviews','photos','_wikipedia'];
```

### F-15 の対応案(あなたが判断)

- 今後のコミット: GitHub の Settings → Emails で「Keep my email addresses private」と「Block command line pushes that expose my email」をオンにし、`git config user.email` を `<ID>+<ユーザー名>@users.noreply.github.com` に。
- 既存のコミット: 公開済みの履歴からの完全な除去には、履歴の書き換え(+ 強制 push、GitHub のキャッシュ・フォーク・クローンへの残存の問題)が必要です。作成者のメールは公開 API で誰でも見られる情報で、リスクは主にスパムや特定です。受け入れるか、リポジトリを作り直すかの判断が必要です(私は書き換えていません)。

### 推奨設定(F-23、あなたが GitHub 上で確認)

- Settings → Code security: **Secret scanning と Push protection** をオン(公開リポジトリは無料)
- Settings → Branches: `master` の保護(PR 必須・CI 必須)。**マージ前に CI が緑**であること
- Settings → Actions → General: ワークフローの権限を「Read repository contents」に(ワークフロー側でも `contents: read` を指定済み)
- Settings → Pages: 「Enforce HTTPS」をオン
